Curator

Sends your library to an LLM, asks what threads run through it, and builds the answers into ordered playlists surfaced as home screen rows.

The library snapshot the model is asked to find threads in.

Items per request. 0 sends the whole library in one request, which is what you want whenever the model's context can hold it: a thread running through items split across two batches is one the model never gets to see, because each call only ever sees its own slice. A director's cut and a theatrical cut are two items in Jellyfin and one film to a viewer. Sent as two they reach the model with identical titles, years, genres and overviews, so it puts both in the same category and the row shows the same poster twice. This keeps the copy with the longest runtime — the fuller cut — and folds the other's watch history onto it, so nothing reads as unseen just because you watched the copy that was dropped. Nothing here is a similarity test: two rows are one title when you have merged them in Jellyfin yourself, or when they carry the same metadata-provider ID, or when kind, title and year all agree — so Freaky Friday (2003) and Freaky Friday (1995) stay two different films. Rows

Curator builds two kinds of row, and each is asked the same two questions: how big is a row, and how many rows. Every number below is also written into the prompt, so the model aims at what it will be judged by rather than having its answer quietly trimmed.

Shared rows

Drawn from the whole library. Every viewer gets all of them.

Keeping rows steady

The model coins largely different threads each run, so a row going missing once usually means the run phrased things differently rather than your taste having changed. Dropping it immediately makes the home screen flicker — the row vanishes and is back the next week. This waits that many runs before a row goes; it still goes eventually if it really has gone. 0 drops it immediately.

None of this touches Recommended for you — that playlist is ranked rather than curated, and its length is Length on the Home screen tab.

Landscape cards are wide, so a short row still fills the screen, while portrait cards fit more across and suit a row worth scrolling. 0 makes every row portrait; a number above the item cap above makes every row landscape.

Worth knowing what else it does: rows sharing an order index are shuffled on every load, so all of Curator's categories in one lane appear in a different order each time you open Jellyfin. In a shared lane they get shuffled into the middle of fifty category rows where nobody scrolls.

Recommendation playlist

One long playlist per viewer, ordered most recommended first, built by merging the categories that viewer already has. Costs nothing — no extra model call — because every category already carries the model's own ordering of its members. Intended for a spotlight banner such as the Media Bar plugin, or any row that takes a playlist name.

Which items appear is always decided by arithmetic over categories you have already paid for — no model call, which is why the playlist is free. The model that shapes that is the one that wrote the categories, and a viewer's own count 1.6× a shared one, so in practice the per-viewer pass model on the Model tab. What a model can add is the order, below.

Rebuilt at the end of every run. Turning this off leaves existing playlists in place rather than deleting them.

Every viewer gets a playlist with this same name — Jellyfin playlists are per-user, so each person sees only their own, and one name in one setting serves everybody. Renaming it here renames the playlists on the next run, so anything pointing at the old name has to be repointed.

Weather and time of day

Two more rows: one for what the weather is doing outside, one for the part of the day it is. Both are worked out when the home screen asks for them, so they always match the actual hour and the actual sky rather than whatever was true at the last refresh. Neither costs a model call — the judgement about what suits a rainy evening was bought once by Judge when an item suits watching on the Summaries tab, which has to be on for either row to have anything to show.

Requires Row source: Curator above. These rows have no playlist behind them — that is what lets them be current to the minute — and Collection Sections can only show a row by naming a playlist, so it cannot serve them. A row with fewer than three matching items is not drawn at all, on the grounds that a single card does not read as a thin row so much as a broken one.
Deliberately a general name rather than one that tracks the sky. A row's title is fixed when the row is registered — at server start and after a run — so a title reading "For a rainy night" would be a claim about the weather several hours ago. The contents are exact; the name should not promise more precision than it can keep.
Shorter than the recommendation playlist on purpose. These rows make a narrow claim — these suit a cold wet evening — and a long one dilutes it with everything that merely qualifies. 0 means no limit.
One place is right for a household watching in one house. Per-viewer is for a library shared across households — and it also moves the time-of-day row onto each viewer's own clock, since the lookup returns the timezone with the forecast. Anyone without a place of their own falls back to the server's.
A place name — Pittsburgh, or Pittsburgh, Pennsylvania if the plain name is ambiguous. Looked up through Open-Meteo, which needs no account and no API key; the coordinates are resolved once and the conditions re-read every half hour in the background, never while a home screen is being drawn. If the name matches nothing, the server log says so and the weather row is simply left out.
A model writes a few titles for each set of conditions and the rows rotate through them, so a rainy evening in March is not labelled identically to one in November. Bought once per set of conditions, not once per refresh: a place produces around thirty distinct conditions, so the cost flattens within a few weeks and then stays flat. A failed call, or a condition seen for the first time while the model is unreachable, falls back to the names above.
Worth pointing somewhere cheap. Naming a shelf is the smallest job anything here asks for — a few dozen words in and a few dozen out.
All of them arrive in one call, so this is variety per unit of spend rather than a multiplier on it. Above about eight the model starts reaching and the last few are noticeably worse than the first.
Titles for conditions that stop occurring are dropped. A year by default, because these conditions are seasonal: culling the snowy-evening titles in July for going six months unused would re-buy them every winter, which is exactly what the cache exists to prevent. 0 keeps them forever. Titles naming a condition Curator no longer recognises are dropped immediately either way — those can never match again.

Condensed summaries

Overviews are about two thirds of every prompt, and the same text is re-sent on every run forever. This rewrites each long overview once into a short summary that keeps the feel of a title rather than its plot, and caches the result. After the first pass only new and rewritten items cost anything. Your library's own overviews are never modified — the short versions live only in Curator's data directory, so clearing them puts everything back exactly.

Tag consolidation

Scraped keyword lists run to about eighteen values an item and are mostly production trivia — aftercreditsstinger, based on novel or book, sequel — mixed with a handful of real mood words. This keeps however many genuinely describe the thing and throws the rest away. Not a fixed count: a title with one clear texture keeps one tag, a dense one keeps several, and an item whose tags are all trivia correctly keeps none.

The whole scraped tag list goes out with the description, and the model writes the rewrite first and then keeps the tags that agree with the reading it just committed to — so the same judgement about how a title feels drives both, and a tag that pulls against the summary gets dropped. Deciding them separately is what gives you a summary calling something quietly devastating next to a tag list saying "action". Done in one model call, so turning this on costs a single pass over the items without consolidated tags yet — not a full redo.
Off by default, and the reason is consistency rather than quality: a tag is only worth something if the same tag means the same thing across items, and free coinage produces near-synonyms — melancholy, melancholic, wistful, quietly sad — describing four films as four textures instead of one. The scraped list is a shared vocabulary imposed for free. Turn this on when you would rather lose that than lose a texture the metadata provider had no word for; the prompt constrains coinage to a last resort and to the plainest wording that fits, so two items with the same feel land on the same word.
A ceiling, not a target — most items should come back with fewer.
A separate decision from building them, and the useful order is to build first, look at what came back below, and only then start paying prompt tokens for them. This overrides Tags per item on the Library tab, which governs the raw scraped list.

When something suits watching

The same judgement the rewrite makes, asked about the room instead of the film: what should the weather outside be doing while someone watches this, and what part of the day does it belong to. It rides along in the call that condenses the description, so it costs almost nothing extra — and it is what fills the two rows on the Home screen tab.

Answers come from a fixed vocabulary — clear, cloudy, rain, storm, snow, fog, hot, cold and morning/afternoon/evening/latenight — because a row asking "is it raining" can only match a word that means the same thing on every item. The model is told to be sparing and that most items should get nothing: a broad comedy suits any hour and any sky, and saying so is the correct answer. Judged in the same call as the description, so switching this on costs one pass over the items not yet judged, not a full redo.

How often each of Curator's scheduled tasks fires. These are the same schedules as Dashboard → Scheduled Tasks — editing here changes them there and the other way round.

Curator

Sends your library to an LLM, asks what threads run through it, and builds the answers into ordered playlists surfaced as home screen rows.

Request

How each call to that model is made.

On by default, and worth leaving on. Turning it off does not simply save tokens: recent models write their reasoning into the visible response instead, which wastes the output budget anyway and produces markedly worse results — a discovery pass returned one usable category instead of twenty with this off. Note the output cap covers thinking and the answer together, so raise Max output tokens rather than turning this off.
Raise this if the log reports truncated batch responses.
Halves the token price by submitting every batch as one asynchronous job, which usually finishes within an hour but is allowed up to 24. This trades against prompt caching rather than adding to it: batched requests run in parallel, so the per-user passes cannot reuse each other's cached prefixes. It also removes the mid-run token budget cutoff, since the whole run is committed up front.

What is sent

The library snapshot the model is asked to find threads in.

Items per request. 0 sends the whole library in one request, which is what you want whenever the model's context can hold it: a thread running through items split across two batches is one the model never gets to see, because each call only ever sees its own slice. Raise it off 0 only if you hit context limits.
Lets the model build episode-level categories. Greatly increases library size and cost.
How many tags to send the model for each item. 0 sends none, which is the default. Scraped tag lists average around 18 values an item and are mostly production trivia ("aftercreditsstinger", "duringcreditsstinger"); they make up roughly 43% of the prompt and pull the model toward the metadata-shaped categories it is told to avoid. Raise this to feed a few of the most relevant ones back in.
Comma-separated collection names. An item in one of these is labelled with it in the item list, so the model can see that a film was, say, an Oscar winner and read that as a signal about the film rather than a fact to file it under. Leave empty to send no collection membership at all. Keep the list short and meaningful: naming a franchise collection here invites exactly the metadata-shaped categories the prompt otherwise tells the model to avoid.

Shared categories

Drawn from the whole library. Every user receives all of them.

Smallest shared category worth keeping, in items, and the size the model is asked to meet. Raise it for fewer, broader rows; lower it to let the model name narrower threads. Minimum 2.
The model coins largely different threads each run, so a category going missing once usually means the run phrased things differently rather than your taste having changed. Dropping its row immediately makes the home screen flicker — the row vanishes and is back the next week. This waits that many runs before a category loses its row; it still goes eventually if it really has gone. 0 drops it immediately, which is how Curator behaved before this setting existed.
Ceiling on how many survive the library-wide pass, strongest first, and the number the model is asked to aim for. Set it generously — the floor above decides what is worth keeping, this only decides how many. A cap the model is not told is one it cannot aim at: given no target count, one model returned 23 categories covering 78% of the library and another returned 5 covering 10%, from an identical prompt. 0 means no cap.

Personal categories

Invented for one viewer from their own watch history.

Smallest category invented for one viewer. Defaults to the same value as the shared floor above. Lower it if invented categories start being discarded on size — a viewer's history is a smaller pool to draw from than the whole library. Minimum 2.
Ceiling on the categories invented for one viewer. Defaults to the same value as the shared cap above. 0 means no cap.

Both pools

Applies to both pools — a category is a home screen row either way, and Collection Sections renders only the first 16 items of one. Members are ranked strongest-first, so anything past this is trimmed off the tail rather than the category being dropped: a forty-item thread becomes the best twenty of itself. 0 means no limit.

Rows

How categories appear on the home screen.

Collection Sections renders collection rows without any ordering control, so playlists are the better choice unless you have a specific reason.
Turn new rows on for target users without them visiting home screen settings. Leave off to have rows appear as available-but-disabled.
Rows with at least this many items render as portrait posters; shorter rows render as landscape thumbs. Landscape cards are wide, so a short row still fills the screen, while portrait cards fit more across and suit a row worth scrolling. 0 makes every row portrait; a number above the item cap above makes every row landscape.

Recommendation playlist

Costs nothing — no extra model call — because every category already carries the model's own ordering of its members. Condensed summaries

Overviews are about two thirds of every prompt, and the same text is re-sent on every run forever. This rewrites each long overview once into a short summary that keeps the feel of a title rather than its plot, and caches the result. After the first pass only new and rewritten items cost anything. Your library's own overviews are never modified — the short versions live only in Curator's data directory, so clearing them puts everything back exactly.

Tag consolidation

Scraped keyword lists run to about eighteen values an item and are mostly production trivia — aftercreditsstinger, based on novel or book, sequel — mixed with a handful of real mood words. This keeps however many genuinely describe the thing and throws the rest away. Not a fixed count: a title with one clear texture keeps one tag, a dense one keeps several, and an item whose tags are all trivia correctly keeps none.

Done in the same model call as the summary, so turning this on costs one pass over the items that do not have consolidated tags yet — not a full redo.
A ceiling, not a target — most items should come back with fewer.
A separate decision from building them, and the useful order is to build first, look at what came back below, and only then start paying prompt tokens for them. This overrides Tags per item on the Library tab, which governs the raw scraped list.
